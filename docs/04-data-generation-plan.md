# 데이터 생성·검증·반복 수집 계획

작성일: 2026-09-18 · 상태: 생성 전 설계. 제시한 건수는 확보된 데이터가 아닌 단계별 제작 목표다. 같은 날 근본 검토를 반영해 로봇 분야의 비중과 rollout 근거 라벨을 늘리고, 결합 행동 후보의 허용 집합 규칙과 안정성 대조 데이터를 추가했다. 이어 [스트리밍 계약](08-streaming-io-and-data-contract.md)에 따라 로봇 데이터를 에피소드 스트림으로 재정의하고, 라벨 필드 분리·미확인 후보·조건부 부가 라벨·DAgger 이력 보존·split 선배정을 반영했다. 충돌하는 세부는 08이 정본이다.

목표는 **상태와 요청별 질문·후보의 의미를 읽고 판단하는 모델**을 학습시키는 것이다. [첫 로봇 작업](02-task-and-learning-problem.md)은 중요한 응용 데이터지만, 전체 학습을 특정 로봇 행동 분류로 제한하지 않는다. 학습 입력·출력은 [모델 계약](03-model-and-training-design.md)을 따른다.

## 1. 데이터 한 건의 정의

레코드는 두 종류다. **단일 요청** 레코드는 `공통 상태 + 질문 묶음 + 질문별 라벨 + 생성 근거`이고 비로봇 분야에 쓴다. **에피소드 스트림** 레코드는 prefix(지시·제약·질문 세트)와 틱 목록으로 이루어지며 로봇 분야에 쓴다. 틱마다 상태·실제 실행 이력·동적 후보, 모델 raw 출력, 하네스 채택 결과, 실행 ACK, 라벨을 분리해 저장한다. 스트림 레코드의 정의와 예시는 [스트리밍 계약](08-streaming-io-and-data-contract.md) 8절이 정본이다.

상태 수, 질문 수, 후보 수, 에피소드 수, 틱 수, 토큰 수를 각각 집계한다. 한 상태를 표현만 바꿔 10번 저장했다고 새로운 상태 10건으로 세지 않는다. 같은 에피소드의 여러 틱은 서로 상관되어 있으므로 독립 표본으로 간주하지 않으며, 로봇 데이터의 독립 단위는 에피소드다.

| 필드 | 저장할 내용 | 모델 입력 여부 |
| --- | --- | --- |
| `request` | 관측 상태, 시각·불확실성, 질문, 타입, 후보·판정 기준. 스트림에서는 실제 실행 이력과 commitment 포함 | 예 |
| `model_output`·`adopted`·`ack` | 스트림의 모델 raw 출력, 하네스가 채택한 답, 실행 ACK | 다음 틱의 실행 이력으로만 |
| `labels` | 정답 ID/허용 집합/분포/관측된 사건 결과, `semantic_admissible`·`unknown`·`label_confidence`·조건(`conditioned_on`), loss mask | 아니오 |
| `provenance` | origin group, episode, simulator·하네스·컨트롤러·전문가·규칙·생성기 버전, seed | 아니오 |
| `evidence` | 규칙 실행 근거, 주석 근거, rollout 요약(seed별 결과)·원본 참조 | 아니오 |
| `split` | train/dev/calibration/test/OOD | 아니오 |
| `usage` | 실제 조합에 사용한 질문과 실행 명령·결과 | 아니오 |

아래는 설명을 위한 최소 예시다. 실제 레코드는 manifest와 원본 증거 파일의 해시도 가진다.

```json
{
  "schema_version": "judgment-v0",
  "origin_group": "scene-family-018",
  "split": "train",
  "request": {
    "request_id": "r018-07",
    "state": {
      "goal": "빨간 물체를 왼쪽 영역으로 옮긴다",
      "observed_at_ms": 1200,
      "objects": [
        {"id": "o7", "color": "red", "visible": true},
        {"id": "o2", "color": "blue", "visible": true}
      ]
    },
    "questions": [{
      "id": "q_target",
      "type": "choice",
      "instructions": "현재 목표에서 옮겨야 하는 물체를 고르라.",
      "criteria": [
        {"id": "c91", "description": "관측된 빨간 물체 o7", "ref": "o7"},
        {"id": "c14", "description": "관측된 파란 물체 o2", "ref": "o2"},
        {"id": "c62", "description": "제공된 정보로 대상을 결정할 수 없음"}
      ]
    }]
  },
  "labels": [{
    "question_id": "q_target",
    "kind": "valid_set",
    "candidate_ids": ["c91"],
    "source": "goal-object-rule-v0",
    "mask": true
  }]
}
```

serializer는 `request`의 허용 필드만 모델에 전달한다. 정답 근거·미래 결과·선택된 행동 로그가 입력 텍스트에 섞이지 않는지 자동 검사한다. 부분 관측 실험에서는 simulator의 실제 물체 위치도 관측 가능한 범위로 제한하고, 하네스 파생 값은 관측된 자세로만 계산한다. 가려진 물체의 참값만 바꿨을 때 입력이 변하지 않는지 검사한다.

## 2. 학습 분야와 판단 형태의 구성

최초 pilot의 상태 비중은 다음과 같이 제안한다. 분야별 전용 모델을 만드는 비중이 아니라, 하나의 판단 모델에 줄 경험의 구성이다. 새 분야의 질문과 후보도 동일한 타입·직렬화 경로를 사용한다. 로봇 폐루프가 첫 응용이자 판단 기준이므로 로봇 상태를 과반으로 둔다. 비로봇 분야는 readout이 로봇 템플릿에 고정되지 않게 하고 의미 일반화를 평가할 만큼만 유지한다. 이전 시작값 `40/30/20/10`은 범용성에 치우쳐 있었다.

| 상태 비중 | 분야 | 질문 예시 | 주된 정답 근거 |
| --- | --- | --- | --- |
| 60% | 로봇·공간 작업(에피소드 스트림) | 매 틱 10질문: 결합 행동 후보의 주 결정, 목표 만족·지시 충분성·관측 필요·재시도의 게이팅, 정지, 그리퍼 상태, 경로·속도·힘. 분해형 비교 구성은 별도 | 스크립트 전문가, 관측 규칙, 기하 검사, 키프레임 틱의 counterfactual rollout |
| 15% | 브라우저·도구 사용의 합성 상태 | 요소·의도·텍스트 후보·실행 조건·진행 수준 | 직접 생성한 DOM/도구 상태와 명시한 사용자 목표 |
| 15% | 업무 흐름·자원 제약 | 다음 단계·담당 자원·충족 조건·우선순위 | 상태 기계, 일정·용량 제약 solver |
| 10% | 일반 판단·추상 규칙 | 지시 충족·모순·순서·예외·정보 부족 | 실행 가능한 규칙 또는 독립 주석 |

브라우저 데이터는 우선 로컬 합성 페이지와 도구 응답을 사용한다. 실제 사용자 계정 조작은 데이터 제작의 전제가 아니다. 사용자 스크린샷은 질문을 나누는 방식의 참고 자료이며, 그 한 화면의 숫자를 정답 데이터로 복제하지 않는다.

비중 60%는 상태 수가 아니라 **step의 유효 loss 비중**으로 관리한다: optimizer step마다 로봇 스트림 단위(에피소드의 TBPTT 구간)와 비로봇 단일 요청 단위(토큰 예산까지 묶은 microbatch)를 **둘 다** 넣고, step 손실을 `0.6·L_robot + 0.4·L_nonrobot`(각각 그 step에 든 로봇 상태들·비로봇 상태들의 평균)으로 계산한다. 누적 토큰 비중을 좇는 방식은 쓰지 않는다 — 에피소드 하나가 단일 요청 수백 개의 토큰과 같아 스트림이 굶는다(Task 5 실측). 로봇 스트림은 틱이 많고 서로 중복되므로 정상 유지 틱은 하향 가중하고 이벤트·목표 변경 틱은 별도로 가중하며, 실제 토큰 비중과 유효 loss 비중을 기록한다. 로봇/비로봇 축과 기존 자료/오류 계열/새 의미 계열의 `70/20/10` 축은 별도 sampler 축이다.

비로봇 단일 요청의 질문 비중 시작값은 choice 60%, boolean 25%, ordinal 15%다. 상태당 질문 수는 `1/4/8/16`을 `10/20/50/20%` 비율로 구성하면 평균 약 8개다. 로봇 스트림은 매 틱 고정 10질문이고 주 결정의 후보 수는 4~32개로 분포시킨다. 분해형 비교 구성은 같은 에피소드에 대한 별도 하네스 버전으로 만든다. 한 질문의 타입과 의미가 고정적으로 연결되지 않게 한다. 한국어·영어와 표현 변형을 포함하되, 번역본은 원본과 같은 split에 둔다.

가정용 에너지 장치 제어처럼 제작 단계부터 학습에서 제외한 분야를 별도 OOD 평가에 둔다. 분야 holdout과 질문 의미 holdout은 구분한다. 공통 상태 안에 필요한 분야 규칙을 제공한 전이와, 사전 지식까지 요구하는 전이도 따로 평가한다.

## 3. 데이터 생성 흐름

```text
분야·장면·의미 계열 설계와 split 배정(생성 전)
  → 상태 생성(단일 요청) / 장면·지시 스크립트·외란 일정 생성 후 스크립트 전문가가 에피소드 실행(스트림)
  → 외부 제작기·하네스가 질문/타입/후보 구성(스트림은 틱마다 요청·채택·ACK 기록)
  → 질문별 정답 근거 산출(스트림은 규칙·전문가·키프레임 rollout, 입력은 바꾸지 않음)
  → 자동 검증(입력/라벨 분리, 정보 경계 포함) + 표본 검수
  → 불변 버전의 dataset manifest
  → 학습/개발 평가
  → train 계열의 오류 수집, 모델 실행 에피소드의 재라벨(split 상속) → 다음 데이터 버전
```

**사건이 잦은 에피소드 (R1, s0.3 · 2026-09-22).** D1의 에피소드는 사건이 거의 없었다 — 36,690틱 가운데 목표 변경은 57틱(0.16 %), 세계 사건이 실린 틱은 1.6 %, `steady`가 80.5 %였고, 완료 뒤 꼬리(1 초)가 틱의 11.8 %를 차지했다. 학습 신호의 0.6 %만이 목표 변경에서 왔다. R1은 다섯 가지를 바꿨다(수치는 `configs/sim/tidy_clutter.yaml`이 단일 출처, 실측 표는 `artifacts/reports/r1-density.json`).

1. **틱 안에서 버려지던 사건의 복원.** 판단 틱 하나는 제어 스텝 5회다. 마지막 스텝의 관측만 남기면 스텝 1~4에서 난 사건이 모델 입력에서 사라진다 — D1의 목표 변경 57번 중 모델이 본 `instruction_changed` 줄은 **7개**였다. 이제 틱 안의 사건을 합친다(`gen-robot-v0.2`). R1에서는 둘이 **같다**.
2. **지시 변경 여러 번.** `instruction.changes`가 v2·v3·v4…를 만들고, 두 번째 변경부터는 가끔 목표 **영역**도 바뀐다(봉인 개념의 영역은 제외 — §5). 변경마다 새 대상(평범한 물체)이고 제약은 **덧붙는다**: 변경 지시는 제약을 다시 말하지 않으므로 모델이 v1의 제약을 기억해야 한다.
3. **외란이 실제로 일어나게.** 창을 에피소드가 **끝나기 전**으로 좁히고(D1의 `[1200, 20000]`은 평균 9.2 초에 끝나는 에피소드에서 절반이 예정만 됐다), 수를 늘리고, `disturbance.target_share`로 그 일부가 **지시의 대상**을 밀게 한다 — 아무 물체나 밀면 대부분 결정과 무관한 사건이다.
4. **프로파일 셋.** E0(사건 없음) 20 % · E1(D1의 값) 40 % · **E2(사건 잦음) 40 %**. E2는 의도한 **스트레스** 프로파일이고 현실적인 빈도는 E1이 든다. E0·E1의 장면·일정은 s0.2와 **비트 단위로 같다**(변경 횟수·영역은 주 난수를 쓰지 않는다) — 그래서 D1의 에피소드를 그대로 재생해 비교할 수 있다.
5. **죽은 꼬리와 정체.** 완료 뒤 꼬리 10 → **3틱**, 그리고 스스로 풀 수 없는 반복을 끊는 **정체 감시**(하네스 `m_observe`/`m_observe_total`/`m_hold`/`m_still`, 재계획 게이트 + 물러남 경로). **h0.9(R1 리뷰 1 C1)**: h0.8의 감시는 순환의 **주기만** 정했다 — `m_hold`=15에서 걸고 commitment를 풀어도 다음 틱에 같은 후보가 그대로 다시 뽑혔고, 한 틱짜리 물러남은 실행기의 힘 반사(접촉력 30N 초과면 속도 계수 0)가 묶어 둔 자리를 벗어나지 못했다. 400편 중 27편이 45 s를 그 순환에 썼고 읽기 틱의 60.6 %가 거기서 나왔다. h0.9는 넷을 더한다. (i) 발동한 결합 키를 `stall_cooldown_ticks`(20) 동안 **후보 목록에서 뺀다** — 후보 집합이 다시 만들어지므로 전문가·모델·라벨이 같은 집합 위에서 답한다. (ii) 한 키의 hold 틱 절대 상한 `m_hold_total`(45, `m_place_total`과 대칭). (iii) 지시 대상의 기하가 `observe_max_age_ms`(8 s)보다 늙으면 관측 게이트가 아니라 **재계획**이다 — 게이트가 영영 뜨는 편과 게이트가 안 뜬 채 유령 기하로 다가가는 편은 같은 결함의 두 방향이다. (iv) 경로 종류와 무관하게 **팔이 멈춰 있는** 틱의 상한 `m_still`(10). 물러남은 `stall_escape_ticks`(5)틱 이어 걸고, 두 틱째에 말단이 `stall_escape_progress_mm`(5)도 움직이지 않으면 결정으로 풀 수 없는 정체이므로 에피소드를 **`stall_exhausted`로 명시적으로 끝낸다**(`max_ms`는 "왜"를 말하지 않는다). 근본 원인도 고쳤다: 관측 자세의 팔이 카메라에서 대상으로 가는 광선을 막아 가시 비율이 0에 고정되던 livelock을 앞단의 **자기 가림 이어 들기**로 푼다(`pw0.2`, `visibility.self_occlusion_carry_mm` — 로봇의 자세는 아는 값이므로 자기 가림은 예측 가능한 결측이고, 그 구간의 **정지한** 물체는 추적으로 이어 든다).

### 상태와 질문을 만드는 주체

규칙 기반 생성기는 사실관계와 제약이 검증 가능한 문제를 만든다. 시뮬레이터는 로봇의 장면·관측·실행 결과를 만든다. 로봇 스트림의 행동은 접근·파지·들기·이동·놓기·밀기 국면과 국소 충돌 검사 기반 경유점을 가진 **스크립트 전문가**가 만들며, 가림·차단 시 규칙으로 관측·보류를 택한다. 놓기는 영역 안의 **빈 자리**(중심에서 가까운, 이웃의 자국과 떨어진 격자점)로 내려가 관측된 바닥이 작업면에 닿는 높이에서 열고, 내려가지 않는 틱(hold·retreat)에는 열지 않는다([스트리밍 계약](08-streaming-io-and-data-contract.md) §4 놓기 규칙). 전문가의 행동 다양성 한계는 D2에서 최적화·RL 전문가와 비교한다. 외부 teacher 모델은 질문의 다양한 표현, 새로운 의미 조합, 혼동하기 쉬운 후보의 초안을 보조할 수 있다. **이 제작기를 학습 중인 판단 모델의 출력 기능으로 옮기지 않는다.**

teacher 출력은 schema 검사, 가능한 경우 규칙·solver, 일부 독립 주석으로 검증한다. 같은 teacher가 문제와 답을 함께 만들고 스스로 동의한 결과만으로 gold라고 부르지 않는다. 모델명·revision 또는 API 버전, prompt, 생성 날짜, 비용, 검증 상태를 저장한다. 검증이 부족한 항목은 weak label로 표시하고 주 평가셋에서 제외한다.

### 후보 제작과 난이도

기초 사례 다음에는 다음 변형을 조합한다.

- 후보 개수·길이·순서·ID를 바꾸고, 정답 위치의 편향을 없앤다.
- 명칭이 비슷하지만 조건이 다른 후보, 한 조건만 위반한 후보, 복수의 허용 답을 포함한다.
- 분해형 비교 구성을 위해 대상 A/B에 대한 조건부 질문을 함께 넣고, 실제 사용하지 않은 분기도 근거가 있을 때 라벨을 준다.
- 필수 정보가 빠진 상태, 오래된 관측, 목표 변경, 후보에 정답이 없는 경우를 포함한다.
- 질문·후보 설명에 낯선 용어가 있어도 상태에 정의가 주어지면 판단할 수 있는 문제를 만든다.
- 의미가 같은 표현 변형과 실제로 정답을 바꾸는 목표·관측 변경을 구분한다.
- 결합 행동 후보는 한 속성만 다른 쌍(같은 대상·다른 접근, 같은 접근·다른 프로파일, 같은 운동·다른 목적지)을 포함해 후보 설명의 차이를 읽어야 답이 갈리게 한다.
- 같은 현재 관측에 다른 이력과 현재 실행 중인 후보를 붙인 대조 상태를 만든다. 실행 중인 후보가 여전히 유효하면 유지가, 새 정보가 있으면 전환이 정답이 되도록 근거를 기록한다.
- 관측 잡음 범위 안의 변형 쌍은 정답이 같아야 하며 결정 안정성 평가에 쓴다. 정답을 바꾸는 변경과 구분한다.
- **대조 sibling(2026-09-19, analysis-nimble §3-2).** 생성기의 1급 산출물이다. 비로봇 4분야는 기본 레코드마다 **사실 하나만** 바꿔(한 필드·값: 물체의 x를 영역 경계 너머 1cm, 요소의 활성·입력값, 단계의 완료, 상황 속성) 질문 하나의 라벨이 뒤집히는 sibling을 같은 문구·같은 origin group·같은 split로 만들고 provenance에 `contrast: {sibling_id, focus_field, flipped_question}`를 적는다(`derivation: contrast`). 쌍은 **삭제 검사**를 지나야 남는다: 초점 사실을 지우면(분야의 `forget` — 관측 없음·읽지 못함·보고 없음·속성 없음) 그 질문의 라벨이 마스크거나 "해당 없음·정보 부족"이어야 한다(규칙 코드가 사실의 부재를 "모른다"로 답한다는 검사; 못 지나면 쌍을 만들지 않고 기본 레코드에 이유를 적는다 — pilot 2,000건·seed 17 실측: 기본 946건 중 767쌍 81 %, 빠짐 no_flip 105·deletion_failed 42·no_contrast 15·sealed_concept 17). sibling 자신의 봉인 근거가 기본 레코드와 달라지는 sibling(봉인 개념을 새로 다루거나 **잃는** 것 — 대칭 규칙, 리뷰 1 M3)은 만들지 않는다(pilot 2,000건에서 `sealed_concept` 31). 로봇은 **틱 대조**(`robo_jev.data.robot_contrast`): 같은 틱 상태에서 코드로 — 지시 대상의 금지 접촉 토글(`q_main`의 적합 집합), 완료 틱의 대상을 영역 경계 너머 1cm(`q_done`), 지시 다음 버전(`q_main`; v2의 대상×영역 조합이 틱의 후보 목록에 이미 있거나 로봇이 다른 물체를 든 틱만 — 후보 목록은 틱의 것이라 하네스가 새 목표에 예약했을 조합이 없는 틱은 하네스가 내지 않는 (상태, 후보) 쌍이 된다, 리뷰 1 I3) — 세 종류다. **지시 종류가 실제로 가르치는 것(리뷰 2 N5):** v2 조합이 목록에 있는 틱은 드물어(batch-0에서 20쌍 중 1) 이 종류는 거의 전부 "로봇이 **아직 이전 대상을 들고 있는데** 새 지시가 다른 물체를 부른다 → 먼저 놓는다(`release_held_object`)"의 쌍이다(batch-0 19/20; `evidence.contrast.main_reasons` keep_commitment → release_held_object). "주 결정이 바뀐다"는 그 뜻이지 "새 대상을 곧장 집는다"가 아니다 — 새 대상×영역 후보로 바로 넘어가는 쌍은 하네스가 v2 조합을 목록에 이미 예약한 틱뿐이고, 그것을 늘리려면 하네스의 재열거 경로(D2)가 필요하다. `q_gripper`를 겨냥하는 종류는 없다: 부가 라벨은 commitment의 국면 프로파일에 조건화되어 든 물체 표지로 뒤집히지 않고, 든 물체 표지를 지우는 뒤집기는 실현할 수 없는 상태(공중의 물체)를 만들며 `q_done`은 경계 이동이 이미 덮는다(리뷰 1 I2). 기본 틱이나 sibling의 `q_main` 답이 퇴화(hold∉A)면 쌍을 만들지 않는다. 기본 틱과 sibling을 `judgment-v0`(state_first, L0) 레코드로 `contrast/records.jsonl`에 쓰고(스트림 틱이 아니다; 후보는 틱의 것, 순서는 섞는다) 에피소드마다 종류별 ≤ 1·합쳐 ≤ `contrast.per_episode`다. **로봇의 삭제 analogue는 대상 삭제다**(리뷰 1 M4): 대상을 관측에서 지우거나 지시의 대상을 비우면 전문가가 판단하지 않고 관측·재계획 게이트로 가야 한다는 검사이지, 뒤집힌 질문의 라벨이 "모른다"가 되는 것이 아니다(boolean에는 마스크가 없고 대상이 없는 `q_done`은 거짓이다). QA는 레코드에 적힌 전문가 버전으로만 이 검사를 다시 돌린다(리뷰 1 M6). 대조 쌍은 한 batch에 함께 들어가도 된다([모델 계약](03-model-and-training-design.md) §4의 상태별 정규화가 처리한다); 학습 sampler는 split별 쌍의 몫을 manifest의 `contrast`에서 읽어 보고한다.

하네스가 준 후보에 정답이 없는데 모델이 만들어낼 수 있다고 기대하지 않는다. `판단 불가` 후보의 존재 여부, 후보 포함률, 잘못된 후보 필터링을 함께 평가한다. 원본 정답이 알려진 변형에서 정답 후보를 제거하면 라벨도 다시 산출한다.

## 4. 라벨의 신뢰 수준과 물리 결과

| 등급 | 예 | 사용 |
| --- | --- | --- |
| 검증 가능한 결정적 라벨 | 명시 규칙·현재 관측·solver가 증명한 답 | train과 주 평가 |
| 관측된 사건 결과 | 정의된 행동·후속 정책의 성공/실패 | 사건 확률 학습·평가 |
| 독립 검수한 의미 라벨 | 주석자 합의와 근거, 허용 답 집합 | 일반 의미 학습·평가 |
| 검증이 부족한 teacher 라벨 | 생성된 판단·선호 | weak-label ablation 또는 검수 대기 |

선택 질문의 정답은 적절한 후보이고, 성공 확률 질문의 정답은 실제 정의된 사건의 결과다. 후자는 다음 정보를 빠짐없이 기록한다.

```text
event_id, observation, action_ref, followup_policy_version,
horizon_seconds, success_rule, randomization_distribution,
rollout_seeds, successes, failures, censored_trials
```

예: 후보 grasp를 실행하고 고정된 lift 동작까지 수행한 뒤 5초 안에 물체를 지정 높이 이상에서 0.5초 유지했는가. 이 시간·높이·후속 동작은 환경 설정에 고정한다. 다른 후속 정책의 결과를 동일 사건으로 합치지 않는다. 정상적으로 5초를 관측했으나 목표를 달성하지 못하면 실패다. worker 중단·인프라 timeout·simulator 오류로 사건을 끝까지 관측하지 못하면 censoring 사유로 보존한다.

관측이 불완전하면 같은 관측에 부합하는 숨은 상태·외란 분포를 명시해 반복한다. 한 번의 결정적 simulator 성공을 `p=1`의 보편적 확률로 취급하지 않는다. 실제 로봇에서 실행하지 않은 행동 결과는 미관측이며, teacher로 채우지 않는다.

### Counterfactual rollout의 제작 예산

모든 틱의 모든 후보에 rollout을 하지 않는다. 에피소드마다 **키프레임 5틱**(이벤트·전술 변경 시점 + 무작위, 사건 종류별 포함률 기록)을 고르고, 그 틱의 결합 후보 중 8개(현재 commitment와 전문가 선택을 반드시 포함, 나머지는 정답을 모른 채 기하 다양성으로 선택)를 같은 목표·horizon·후속 정책 아래 paired seed로 실행한다. rollout하지 않은 후보는 `unknown`으로 두고 부분 라벨 손실로 학습한다. 목록에 정답이 없을 가능성은 후보 포함률로 별도 평가한다.

| 단계 | 에피소드 | 키프레임 상태 | 상태당 결합 후보 | 반복 seed | rollout 수 |
| --- | --- | --- | --- | --- | --- |
| D1 | 400 | 2,000 | 8 | 8 | 128,000 |
| D2 | 4,000 | 20,000 | 8 | 16 | 2,560,000 |

한 rollout의 평가 구간이 5초라면 각각 약 178시간·3,556시간의 모의 시간이다. 실제 제작 시간은 병렬 worker 수, reset·snapshot 복원, 후속 정책 비용, 시뮬레이션 속도를 측정해 계산하고, 첫 100개 rollout의 실측으로 CPU 비용을 다시 산정한 뒤 D2 규모를 확정한다. 기본 구조화 상태 제작에는 영상 렌더링을 끄고, 검수·인식 실험에 필요한 장면만 저장한다.

8회·16회 반복으로 개별 상태의 정밀한 성공 확률을 안다고 주장하지 않는다. seed 8회는 초기 선별용이며 근소한 후보 차이를 판정하는 표본 수가 아니다. 성공·실패 횟수를 seed별로 보존하고 신뢰구간을 계산하며, 경계 사례는 추가 표본을 모으거나 넓은 불확실성을 유지한다. censoring으로 유효 반복 수가 다르면 그 수로 계산하되 censoring이 선택적일 수 있으므로 사유를 보존하고 편향을 검토한다.

주 결정의 허용 집합은 세 단계로 산출한다. (1) 지시·목적지·금지 조건으로 `semantic_admissible`을 정한다. (2) 적합 후보 안에서만 성공률과 불확실성을 비교한다. (3) 현재 commitment가 적합하고 최고 후보와의 성공률 차이가 허용 여유 `ε=0.15` 이내이며 성공률 하한이 0.5 이상이면 그 후보만 정답으로 둔다. 근거가 약하면(구간이 넓거나 rollout 집합에 없음) 유일 정답 대신 복수 허용·추가 rollout·낮은 `label_confidence` 중 하나를 쓴다. 관측·보류·재계획 후보는 규칙 라벨로만 정답이 되며 사건 성공률과 비교하지 않는다. 적합성 규칙은 추론 시 후보 생성기에 넣지 않는다. 규칙 버전과 원시 횟수를 함께 보존해 나중에 다른 규칙으로 다시 산출할 수 있게 한다. 같은 횟수는 사건 확률 질문의 Bernoulli 라벨로도 쓰되, 두 라벨을 한 분포로 합치지 않는다. 부가 질문(그리퍼·경로·속도·힘)의 라벨은 그 틱의 실제 commitment에 조건화한 전문가 답이며 규칙은 [스트리밍 계약](08-streaming-io-and-data-contract.md) 7절을 따른다.

## 5. 분할과 누출 방지

분할은 표현 증강과 인접 frame 추출보다 먼저 하며, 로봇 스트림은 장면 계열의 split을 **에피소드 생성 전에** 배정한다. `origin_group`에는 원본 장면/에피소드, 목표 생성 계열, 원본 문서·페이지의 계보를 담는다. 파생 번역·질문 재표현·후보 재배열·counterfactual sibling, 같은 에피소드의 틱·rollout·학습 구간·재라벨링 파생본은 모두 같은 split을 따른다.

| 분할 | 기본 비중 | 용도 |
| --- | --- | --- |
| Train | 70% | 가중치 업데이트, 오류 기반 보강 |
| Dev | 10% | LR·학습 기간·구조·checkpoint 선택 |
| Calibration | 10% | 확률 보정·실행 임계값 선택 |
| ID Test | 10% | 최종 동결 비교 |
| OOD (`ood_dev` / `ood_test`) | holdout으로만 | 미학습 의미 계열·후보 조합·분야 평가. 계열 해시로 반분 — `ood_dev`는 개발용, `ood_test`는 봉인 |

먼저 의미 계열·분야 holdout을 통째로 제외한 뒤, 나머지를 origin group 단위로 기본 split에 배정한다. holdout에는 **템플릿 변형 계열**(같은 개념의 다른 표현)과 **개념 계열**(분야마다 개념 하나를 통째로)을 둘 다 둔다; 필드 집합만 다르고 개념 어휘를 공유하는 test는 새 의미를 검증하지 못한다. OOD는 계열 해시로 `ood_dev`(개발용)와 `ood_test`(봉인)로 반분한다. D2는 D1의 계보와 분할을 승계하며, 이미 학습한 D1 에피소드·상태를 새 test로 재배치하지 않는다.

**봉인 목록 (2026-09-19, 계약 v0.3 — `configs/data/pilot.yaml`·`d1_robot.yaml`의 `split` 절이 단일 출처).** 생성기가 레코드마다 provenance에 문구 템플릿 변형 id(`phrasing`; 로봇은 `instruction_templates`)와 개념 id(`concepts`)를 적고, 한 계열의 레코드 중 하나라도 아래 목록에 걸리면 계열 전체가 OOD로 간다(한 group이 두 split에 걸치지 않는다 — 검사: pilot 2,000상태와 로봇 400편 일정 모의에서 걸친 group 0). 로봇 계열의 origin group은 `robot/<profile>/<장면 계열>/goal-<목표 영역>`이라 목표 생성 계열이 계보에 든다; 로봇 지시의 문구 변형은 난수가 아니라 **이 group의 해시**가 정하므로(v1·변경 따로) 같은 group의 에피소드는 같은 변형이고 템플릿 holdout도 group을 가르지 않는다(리뷰 1 I1). **s0.3이 지시를 여러 번 바꾸게 되면서 이 규칙이 두 번 깨졌고 둘 다 400편 QA가 잡았다**: (a) 도중 변경이 목표 영역을 zoneF로 바꾸면 같은 계보의 한 편만 봉인돼 group이 갈렸다(400편 실측에서 **27 group이 영향을 받았고 그 가운데 13 group(32편, 소수 쪽 13편)이 실제로 두 split에 걸쳤다** (리뷰 1 I2 — 27은 도중 변경이 `zoneF`를 들여온 group 수다)) → `instruction.zone_change_excludes`; (b) 프로파일마다 seed 계수기를 따로 두면서 **같은 수**를 주어 E1과 E2가 같은 장면을 냈다(E1 6~10물체·E2 7~10물체는 장면 추첨이 겹칠 수 있다) → `seeds.profile_offset`. 둘 다 시험으로 고정했다(`tests/test_robot_episodes.py`). **OOD의 몫은 ≈10~15 %**(사용자 결정; 비로봇은 분야별 계열 기준, 로봇은 D1 규모의 에피소드 기준)이고, 봉인 종류·id는 그대로 두고 **생성 비중**으로 맞춘다: 봉인 문구 변형은 그 표에서 `sealed_phrasing_share`(10 %)만큼만 뽑히고, 봉인 개념의 근원이 되는 장면(가운데 영역 목표 `_GOAL_ZONE_WEIGHTS` 45/10/45, 접힌 구역 `template_weights` 45/10/45, 자원 부족 42.5/15/42.5, 안내 요청 조치 `_RULE_ACTION_WEIGHTS` 30/30/24/30; 로봇은 `goal_zone_weights` 48/48/4와 `template_weights` 46.5/46.5/7)은 드물게 둔다. 자동 QA(`python -m robo_jev.data.validate`, 데이터셋의 `manifest.json`에서 목록을 읽는다)가 종류별 계열·레코드 수를 세고, holdout 계열이 train/dev/calibration/test에 있으면(누출) 또는 OOD인데 이유가 없으면 위반이다. 봉인 id는 값의 예시가 아니라 **id**로 적는다.

분야별 합집합(계열 기준, pilot 2,000상태·seed 17): spatial 10.8 % (41/378, ood_dev 17 / ood_test 24), dom 10.6 % (40/377, 18/22), workflow 12.0 % (47/393, 26/21), rules 12.5 % (48/384, 23/25) — seed 18·19에서는 분야마다 8~17 %로 흔들린다(개념 계열은 장면의 우연에 따른다). 대조 sibling(§3)을 더한 뒤의 pilot 2,000건(seed 17)은 기본 951건 + sibling 760건 + 번역·재배열본이라 계열이 227~247개이고 봉인 몫은 spatial 11.0 / dom 10.4 / workflow 12.6 / rules 11.8 %다(sibling은 계열의 봉인 근거를 더하지도 잃지도 않는다 — 대칭 규칙). **비로봇 규모의 단위(리뷰 1 M8):** 이 문서의 `2,000 → 8,000 → 20,000상태`는 **기본 상태**(base records)의 수다. 생성기의 `--count`는 레코드 수(기본 + 대조 sibling + 번역·재배열본)라 기본 상태는 그 ≈ 47 %(pilot 951/2,000)이고, 목표는 manifest `counts.contrast.base_records`로 확인한다 — D1의 2,000 기본 상태는 `--count` ≈ 4,200이다. 로봇: 400편 일정 모의에서 58/400 = 14.5 % (ood_dev 24 / ood_test 34; E0 21/200, E1 37/200), 2,000편 모의에서 11.7 %; 재생성한 batch-0(40편)은 5/40. 비율은 pilot 설정 2,000상태(seed 17)·d1_robot 일정(seed 100~)의 실측이다. 분야별 개념·문구 어휘 전체는 `robo_jev.data.domains.CONCEPT_VOCABULARY`·`phrasing_vocabulary()`에 있다(spatial: target·nearest·in_zone·goal_met·distance·crowding + goal-zone; dom: action·blocker·reachable·needs_input·actionable·progress + reveal; workflow: next·owner·precondition·blocked·priority·load + resource_offline; rules: governing·action·conflict·enough·applies·severity + escort-policy). 주 질문 문구(target·action·next·governing)의 변형은 계열의 2/3 이상이 쓰므로 봉인하지 않았다 — 그것을 봉인하면 train이 사라진다.

**은퇴 규칙.** `ood_test`는 봉인이다: 그 오류를 다음 데이터 생성(계열 추가·규칙 수정·홀드아웃 재선정)에 쓰면 그 test 버전을 은퇴시키고(목록의 id를 바꾸거나 새 계열을 봉인해) 새 `ood_test`를 만든다. `ood_dev`는 개발에 쓴다. 이미 학습한 계열을 새 test로 재배치하지 않는다.

생성기는 레코드마다 **혼동 후보**(표면 특징이 정답과 겹치는 방해 후보: 같은 색·같은 종류의 다른 물체, 이름이 비슷한 다른 항목 등)를 하나 이상 넣고 그 사실을 provenance에 기록한다. 정확한 중복 hash뿐 아니라 정규화된 사실·목표·제약·생성 template의 유사성도 검사한다. holdout이 단지 물체 이름과 후보 ID를 바꾼 버전인지 검수한다. test 오류를 다음 데이터 생성에 사용하면 그 test 버전을 은퇴시키고 새로운 봉인 test를 만든다(위 은퇴 규칙).

학습에서 실패·희귀 사건을 과대표집하더라도 calibration과 운영 성능 평가에는 목표 운영 분포를 반영한다. 빈도 정보를 보존하고, 자연 분포 성능과 균형 challenge 성능을 별도 보고한다. 운영 분포가 아직 없으면 가정한 분포를 명시하고 그 범위에서만 확률 보정을 주장한다.

| D3+ | 재라벨링 200 에피소드 단위 증분 | 10K 단위 증분 | 실측 집계 | 오류 분류에 따른 목적 있는 추가와 기존 성능 유지 |

질문 수는 설계상의 근사치이며 틱은 독립 표본이 아니다. 제작 manifest에는 실제 집계를 쓴다(D1 행은 실측으로 고쳤다: 에피소드가 평균 9.2초에 끝나 틱은 설계의 30 %다 — 학습 토큰 예산·rollout 산정은 그 수로 한다). D2가 모델의 모든 일반화를 확보하기에 충분하다는 전제도 두지 않는다. 에피소드 `400 → 1,600 → 4,000`과 비로봇 상태 `2K → 8K → 20K`의 학습 곡선을 보고 다음 규모를 결정한다.

자동 QA에서는 schema 위반, 존재하지 않는 정답 ID, 잘못된 확률 합·범위, ordinal 순서 오류, 중복 계보, 미래 정보 유입, 가려진 참값의 파생 값 유입, 실행 이력과 라벨의 혼동(스트림), `action_ref`·국면 참조 불일치, 손상된 evidence를 검사한다. **대조 쌍의 관문(§3):** sibling마다 부모가 같은 계열·split에 있고, 표현을 걷어낸 상태가 부모와 정확히 한 자리(로봇 틱은 초점 사실과 그 파생값)만 다르며, 뒤집혔다는 질문의 라벨이 실제로 다르고, 초점 사실을 지운 장면에서 규칙 코드(로봇은 전문가)를 다시 돌려 라벨이 마스크·"해당 없음"(로봇은 관측·재계획 게이트)이 되는지 확인한다 — 삭제 검사에 실패한 쌍은 생성기가 만들지 않으므로(빠진 이유를 기본 레코드와 manifest에 센다) QA의 실패는 생성기와 규칙 코드의 불일치다. 쌍 수·split·분야별 수·삭제 결과·빠진 이유를 보고서의 `contrast`에 적는다. 위반 건수는 0이 되어야 배포 가능한 데이터 버전으로 동결한다.

D1은 최소 500개 질문을 분야·타입·난이도별로 검수한다. 각 핵심 층에 최소 30개를 확보하느라 500개를 넘으면 확대한다. 100개 이상은 두 사람이 독립 판정한다. 중대한 오라벨 2% 미만을 임시 통과 기준으로 삼고, 누출이 발견되면 해당 계열 전체를 재생성한다. 희귀 오류의 신뢰구간도 보고하며 표본 검수만으로 오류 0%를 주장하지 않는다.

## 7. 지속적인 학습·실험 사이클

매 사이클은 `실패 묶음 선택 → 근거 확인 → train 계열에서 변형 생성 → QA → 데이터 버전 고정 → 학습 → 회귀 평가 → 채택/보류`다. 원본 에피소드 수와 새로운 의미 계열 수가 늘었는지 함께 확인한다.

로봇 스트림에는 **DAgger식 재라벨링**을 D1 직후부터 넣는다. 학습 버전마다 모델을 시뮬레이션에서 200 에피소드 실행하고, 방문한 틱에서 전문가·규칙이 지금 고를 답을 labels에만 기록한다. 레코드의 모델 raw 출력, 하네스 채택 결과, 실행 ACK, 실행 이력·commitment는 실제 실행된 것을 그대로 보존한다. 새 에피소드에 정책 오류·복구 상황·commitment 변경이 얼마나 포함됐는지 집계한다.

첫 혼합 비율은 이전 검증 데이터 70%, 새 오류 계열 20%, 새로운 의미 계열 10%로 둔다. 이 축은 로봇/비로봇 비중 축과 별개다. 실제 오류 분포에 따라 dev에서 조정한다. 매번 최신 오류만 학습해 기존 판단을 잊지 않게 한다. 이전 checkpoint와 동일한 평가셋으로 비교하고, 개선 근거가 없으면 기존 모델을 유지한다.

산출물은 `manifest.json`, 불변 Parquet/JSONL shard, split 계보, 라벨 근거 참조, QA 보고서, 제작 비용 집계다. 이 데이터를 읽는 학습기는 입력을 다시 생성하거나 teacher를 호출하지 않아야 동일 실험을 재현할 수 있다.
